# Building Markdown_with_Mermaid

Use a 64-bit Windows development machine with PowerShell and curl.exe.
Zig builds both x64 and x86 DLLs; the end user does not need the build tools.

```powershell
./bootstrap.ps1
./build.ps1 -Profile Release
./tools/check-release-package.ps1
node tests/check-binaries.cjs
```

Bootstrap downloads pinned Zig 0.13.0 and WebView2 SDK 1.0.2903.40, verifies their
SHA-256 hashes, and checks the bundled Mermaid 11.16.1 hash. Tools stay in `tools`;
compiler caches and generated headers stay in `build`. A cold toolchain build
can emit warnings from bundled libunwind; build failures stop the script.

`VERSION` is the version source. The build generates the numeric Windows
VERSIONINFO resource, About version and HTTP User-Agent. For 1.4.1 the numeric
DLL version is 1.4.1.0. Release mode is the default and strips debug information.

Release output:

```text
build/bin/x64/Markdown_with_Mermaid.dll
build/bin/x86/Markdown_with_Mermaid.dll
dist/x64/Markdown_with_Mermaid/
dist/x86/Markdown_with_Mermaid/
dist/Markdown_with_Mermaid-<version>-x64.zip
dist/Markdown_with_Mermaid-<version>-x86.zip
dist/SHA256SUMS.txt
```

Each ZIP contains the main DLL at its root. It also includes browser assets,
the architecture-matched WebView2 loader, licenses and user documentation.
The checksum file covers only the archives generated by that packaging run.
The package check verifies version, author, ZIP layout, hashes, required files
and the absence of a compiled workspace path.

For x64 only, add `-SkipX86` and run the package checker with `-Architecture x64`.

## Local development

`./build.ps1 -Profile Development` embeds the workspace `runtime` directory as
a development default and builds DLLs without automatically publishing ZIPs.
The public packager accepts only current Release build metadata and DLL versions.

An explicit `DataDirectory` in the module INI takes precedence in either mode.
The development helper `install.ps1` copies the staged Release files and writes
that override to keep data inside the workspace. It requires Notepad++ to be
closed and may require elevation when targeting Program Files. It is not a
prerequisite for installing the public ZIP or using Plugins Admin.

Changing tool versions or browser bundles requires updating their pinned hashes,
source records and third-party notices. Keep copyright/license comments embedded
in bundled JavaScript. Do not regenerate assets from floating dependency versions
when reproducing a release.

Toolbar icon resources can be regenerated with Node.js and sharp:
`node tools/build-toolbar-icon.cjs`. These are optional development tools;
the generated SVG, ICO and BMP files are already included in the source tree.

See [testing](TESTING.md) before preparing a release tag.

A GitHub Actions template is provided in [BUILD-WORKFLOW.yml](BUILD-WORKFLOW.yml).
It builds both architectures and checks packages and PE imports on Windows
Server 2022, without uploading binary artifacts, creating a tag or publishing a
release. It does not perform desktop/WebView2 acceptance tests or establish
compatibility with Windows 11.

The template is not active in this repository. To enable CI, a maintainer can
copy it to `.github/workflows/build.yml` and commit the change with the
appropriate repository permissions. A successful workflow checks the build;
desktop/WebView2 acceptance remains a separate step.
